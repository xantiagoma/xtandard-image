# Roadmap

Each work package (WP) becomes one GitHub issue and one PR. WPs are sized for one coding agent (roughly ≤ 1,500 lines including tests), own a directory, and talk to other WPs only through the interfaces in `ARCHITECTURE.md`. A WP may start as soon as its dependencies' **interfaces** are merged (every foundational WP lands its interface file first as a tiny PR), so most of a milestone runs in parallel.

**Status** (as of 2026-09-28, checked against the code and the pull requests): **done (#N)** merged into `main` in pull request N (M2 landed as one merge, #79; the closed per-package PRs #50–#78 describe each package; M3 landed as the `m3` stack #80–#92, merge 893b191); **in PR (#N)** open pull request N, not on `main` yet; **in progress** assigned and being worked on; **planned** not started; **partial** / **dropped** carry a note. Update the column in the pull request that changes it.

**Where things stand:** M1, M2 and M3 are complete on `main` (PR #93 closed M3). M5 (video transformations, ADR 0012) started on 2026-10-04; its foundation (WP-120 FFmpeg base, WP-121 video subsystem core) is done on `m5/foundation-integration`; the URL syntax and options (WP-122) and audio (WP-123) on `m5/wp-122-123-video-options-audio`. The `full` and `gpl` images are built and verified locally; their multi-arch publish waits for GitHub Actions to be re-enabled.

**IDs are stable.** A WP keeps its ID forever. A split adds a letter suffix (`WP-21b`); new work takes an unused number; a WP moved between milestones keeps its number. Never renumber.

Universal done criteria (not repeated below): code follows `docs/go-standards.md`; `go test -race ./...` and every CI gate in `CLAUDE.md` pass; pure-Go packages pass with `CGO_ENABLED=0`; exported API documented; fuzz target for every parser/decoder; docs (`CONFIG.md`, `URL-DIALECTS.md`, `FORMATS.md`) updated when behaviour or config changes; integration tests use `//go:build integration` against `docker compose` services (go-standards §8), never testcontainers.

## M1: core

Goal: a runnable, multi-arch `slim` image on GHCR that serves the imgproxy dialect end to end (plus the query dialect) from all source types, with the core processing set, all still formats except RAW/PDF/PSD (M2), signing, encryption, mandatory allowlist, SSRF protection, admission control, metrics and health endpoints.

Critical path: WP-01 → WP-05 → **WP-00 (walking skeleton)** → WP-06 → WP-26a → WP-34a → WP-37 → WP-39. WP-00 retires the integration risk (cgo + libvips + Docker + multi-arch) before anything else is built on top of it.

## Open questions for the owner

1. ~~**H.264 for GIF→MP4 (WP-76).**~~ **Resolved (2026-09-27):** H.264 encoding (libx264) exists only in the opt-in `gpl` image flavor (WP-70b, ADR 0006 amendment); `full` keeps WebM/VP9 and AV1-in-MP4, and openh264 is not pursued. The encoder is detected at runtime ([FORMATS 5.1](FORMATS.md#51-video-output-wp-76)).
2. ~~**HEVC patents.**~~ **Resolved (2026-09-27):** HEVC video encoding (libx265) exists only in the `gpl` flavor, whose deployer is responsible for the patent review (stated in the README and the image's `LICENSE-GPL.md`). slim and full keep HEVC/HEIC decode, and HEIC encode (kvazaar) stays behind `XI_HEIC_ENCODE` (default off).
3. **Invalid-URL status.** imgproxy answers 404 for malformed or unknown options. We plan 400. Proposal: 400, with an `XI_DIALECTS_IMGPROXY_STRICT_COMPAT` switch that restores 404.
4. **Upload/POST processing** (imaginary `POST /resize`, multipart). Out of scope so far. Should it be in M2?
5. **OpenStack Swift source.** imgproxy supports it. Is it needed?
6. **Default for unsigned foreign dialects.** `restricted` is safe but surprises users who expect arbitrary sizes. Should the default stay `restricted`?
7. **Object-detection model.** Proposal: YOLOX-s (Apache-2.0) plus YuNet (MIT). The alternative is RT-DETR/D-FINE (Apache-2.0), which is more accurate but slower.

8. ~~**Playground (WP-80).**~~ **Resolved:** inside the server binary, off by default (`XI_PLAYGROUND_ENABLED=false`), on the admin listener at `/_playground/` and on the public listener only with `XI_PLAYGROUND_PUBLIC=true`; plain HTML/CSS/JS embedded with `go:embed`, no bundler, npm or CDN (air-gapped, CSP `default-src 'self'`). Signing happens server-side ([CONFIG.md](CONFIG.md#playground)).
9. ~~**Public schema/spec URL (WP-81b).**~~ **Resolved:** the GitHub Pages URL is the `$id`, and the binary also serves its embedded schema at admin `GET /config.schema.json` (and `config schema` prints it), so a self-hosted instance can point editors at its own URL (ADR 0007 decision 6).
10. ~~**TypeScript package (WP-84).**~~ **Resolved:** stay in this repo, with a root Bun workspace over `packages/*` (the Grafana and terraform-cdk convention; `clients/` has no precedent). The first package is `@xtandard/image-url` in `packages/image-url`, in the owner's existing `@xtandard` scope with an `image-` prefix ([ADR 0009](adr/0009-typescript-monorepo.md)).
11. ~~**Secrets in config files (WP-81).**~~ **Resolved:** secret-typed values accept `{file: /abs/path}`, which works like `XI_…_FILE` for one value. `${file:…}` string interpolation was rejected because it collides with Compose interpolation (ADR 0007 decision 7).
12. ~~**huma handlers (ADR 0008).**~~ **Resolved:** builder-only in WP-82. The WP-82b spike moves JSON endpoints to huma handlers only if huma's own errors can emit our `errs` envelope and status without huma globals and without regressing go-standards §2. Image endpoints and `/info` stay hand-written regardless (ADR 0008 decision 5). **Spike outcome (WP-82b):** rejected. The envelope and status were reachable only through an undocumented ordering inside huma, `/healthz` went from 12 to 17 allocations and about +57% latency, huma can still write to stderr or panic on a failed write, and its generated error docs come from the `NewError` global. huma stays builder-only.
